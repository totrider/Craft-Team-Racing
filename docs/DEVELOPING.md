# Developing Craft Team Racing

How to set up, build and change the mod. The working rules are in [../CLAUDE.md](../CLAUDE.md); this guide explains the parts behind them.

**Contents:** [What you need](#what-you-need) · [Layout](#layout) · [Building](#building) · [How the files fit together](#how-the-files-fit-together) · [Common jobs](#common-jobs) · [Known quirks](#known-quirks)

## What you need
| Tool | For |
|---|---|
| **JDK 21** | Building the mod (the Gradle wrapper does the rest) |
| **Python 3 with Pillow and numpy** (`pip install pillow numpy`) | The generators in `tools/` and the texture build |
| **Krita** | Optional. Opening the layered `.kra` files; also its sRGB colour profile (used when writing them) and its Ogg DLLs (used for the synthesised sounds; set `KRITA_BIN` if it is elsewhere) |
| **Blockbench** | Editing the box models in `blockbench/` |
| **Blender** | Only for the mesh models in `blender/`. Without it the committed exports are used as they are (set `BLENDER` to its path if it is not in Program Files) |
| **A NeoForge 21.1 instance** | Testing. `build-and-install.ps1` lists the instances it copies the jar into (edit them at the top) |

## Layout
| Folder / file | What is in it |
|---|---|
| `src/main/java/com/craftteamracing/` | The mod. `physics/` is the port of the original's physics and must not import Minecraft or NeoForge classes |
| `src/main/resources/` | Assets and data. Most of the JSON (models, blockstates, recipes, tags, loot, lang) is **written by the generators**; the PNGs come from the texture build |
| `src/test/` | Unit tests (physics, terrain, tracks, upgrades) |
| `blockbench/` | **Source** of the box models, one folder per family. See its README |
| `blender/` | **Source** of the mesh models (`.blend`). See its README |
| `krita/` | Layered Krita files for the textures: **templates for modders**, generated by the art scripts. See its README |
| `tools/` | The generators, the texture build and their libraries. See its README. `tools/blender/` runs inside Blender; `tools/ctr_disc/` reads the user's own game disc |
| `scripts/` | Launchers (`.bat`) for the disc tools, which build local resource packs |
| `asset-extractor/` | A folder to drop into an instance that builds those packs without the source tree (its `ctr/` is generated by `tools/ctr_disc/package_asset_extractor.py`) |
| `modpack/` | Assets for the mod and modpack pages: the icons, the title, the instance icon |
| `docs/` | These documents. `docs/img/` holds the generated pictures (recipes, power-ups, the icon) |
| `reference/`, `local-assets/`, `run/` | Local only, git-ignored: checkouts of the sources the port reads, packs made from the user's disc, the dev run folder |
| `build-and-install.ps1` / `.bat` | Runs the generators, builds the jar and copies it into the test instances |

## Building
- `build-and-install.bat` is the normal build: every generator, the texture build (`tools/build_art.py`), `gradlew build`, then the jar is copied into each test instance. Close the game first,
  because Minecraft locks the jar while it runs.
- `gradlew build` alone makes `build/libs/craftteamracing-<version>.jar`; `gradlew test` runs the unit tests.
- `python tools/build_art.py` rebuilds only the textures (`--check` writes nothing and fails if a PNG is out of date; `--only <text>` limits it to some `.kra` files).
- The version is `mod_version` in `gradle.properties`; add each release to [../CHANGELOG.md](../CHANGELOG.md).

## How the files fit together
The rule is: **edit the source, never the generated file.**

| You edit | A script turns it into | Notes |
|---|---|---|
| a `.bbmodel` in `blockbench/` | the model JSON, plus blockstates, item models, loot, tags and lang | the `tools/make_*.py` generators read it |
| a `.blend` in `blender/` | `models/item/*.obj` + `.mtl` and the `pickup_*.json` that point at them | `tools/export_blender_models.py` |
| an art script in `tools/` | a layered `.kra` in `krita/`, then the PNG | see below |
| the recipe files in `src/main/resources/data/craftteamracing/recipe/` | the crafting-grid pictures in `docs/img/recipes/` | `tools/make_recipe_grids.py`; rerun it after a recipe or an icon changes |

### Textures: script → layered `.kra` → PNG
- The **art scripts are the source of truth** for the shipped textures. Each draws its picture into named layers and writes a whole layered `.kra` file (`tools/kra_writer.py`); then
  `tools/build_art.py` flattens it into the PNG, as `krita/manifest.json` says. Never hand-edit a generated PNG.
- The `.kra` files are **templates and baselines for modders**: copy them out of the project, edit them in your own folder, and use the result as hand-made art, a resource pack override or
  the start of a variant. They are not edited inside the project, and each is rewritten from its script whenever the script (or something it imports or reads) changes, tracked by a
  stamp in `krita/.stamps.json`; so they never go stale and a small change does not rebuild every file. `python tools/kra_stamp.py --status` lists them; `--force` rebuilds all.
- Some pictures are **derived** from others and written directly by their script: the outlined 96 x 64 HUD icons (`tools/sprite_outline.py`), the glow maps and Fusion's pieced sheets of the
  boost pads, the burst's copies, the kart's ground shadow.
- If you paint something by hand, tell Claude what you changed: it is carried into the script as faithfully as the script's rules allow (approximately: the scripts are rule-based, not
  pixel by pixel). The same goes for a hand change to a Blockbench model.

### The original game's assets
Original textures, sounds, music and models are never in the repository or the jar. `scripts/extract-ctr-*.bat` (and the `asset-extractor` folder) build local, git-ignored resource packs from
the user's own disc with `tools/ctr_disc/`. The mod ships synthesised placeholders (`tools/make_sounds.py`, `tools/make_jingles.py`).

## Common jobs
- **Change a texture:** edit its art script (find it from the `.kra` name in `krita/manifest.json` or from `tools/README.md`), run the build. A change you drew by hand is described to Claude.
- **Change a box model:** edit the `.bbmodel` in Blockbench, save, run the build. Do not edit the generated JSON.
- **New block or item:** a Blockbench model first, then a generator that reads it, then the registry entry (`ModBlocks` / `ModItems`) and a lang key. A texture gets an art script that writes
  its `.kra` (use `tools/kra_layers.py`) and an entry in `krita/manifest.json`.
- **Add a recipe:** the recipe file, then `python tools/make_recipe_grids.py` for its picture.
- **Export a few textures as PNG files:** `python tools/build_art.py --only <text> --out <folder>`.

## Known quirks
- Python steps occasionally fail once with `OSError: [Errno 22]` when Windows briefly locks a file that was just written. `build-and-install.ps1` runs a failing generator again, up to four times.
- `make_boost_pad.py` and `make_survival_assets.py` both fill the vanilla tags `slabs`, `stairs` and `mineable/pickaxe`: each adds its entries to what is already in the file, in
  whichever order they run. A block that is renamed or removed has to be taken out of those files by hand.
- Scripts that rewrite `lang/en_us.json` may drop or add its trailing newline; the content is the same.
- Hand edits to a generated PNG or JSON are lost at the next build.
